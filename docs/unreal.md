The project targets **Unreal Engine 5.8.3**, changelist **58210709** (the exact pin is in [toolchain](toolchain.md)), Windows and macOS. An offline prototype is in source. On 2026-09-25 the main checkout built the Mac editor target with the pinned engine, and `scripts/toolchain/import-mac.sh` imported the source art. The editor validator then loaded all **277** manifest-declared packages with their expected Unreal types and material bindings, and all nine `SoraArena` automation tests passed in the editor (see [Headless automation](#headless-automation)). Before the re-pin, an isolated diagnostic worktree built the Mac editor and game targets with the same installed 5.8.3. Its latest cook completed with **795 packages** and seven platform skips, and UAT staged a signed Mac app with bundle identifier `org.sora.soraarena`, whose headless runtime test reported `lods=3 materials=23` and exited successfully. Nothing has yet been cooked or packaged from the main checkout. These are import, binding, compilation, cook and startup checks; gameplay appearance, frame rate and the Windows build remain open. Xcode 26.1.1 is installed for macOS. An earlier diagnostic attempt using 5.2 stopped at SDK validation before compiling source.

## Rendering configuration and acceptance gate

The source-controlled rendering path is defined in `Config/DefaultEngine.ini`,
`Config/Windows/WindowsEngine.ini`, `Config/Mac/MacEngine.ini`, and
`Config/DefaultScalability.ini`. Unreal loads the platform Engine file after the
project default, and project scalability sections customize the engine's
High (`2`) and Epic (`3`) tiers. This follows Epic's [configuration hierarchy](https://dev.epicgames.com/documentation/unreal-engine/configuration-files-in-unreal-engine),
[scalability reference](https://dev.epicgames.com/documentation/unreal-engine/scalability-reference-for-unreal-engine),
and [device-specific optimization guidance](https://dev.epicgames.com/documentation/unreal-engine/optimizing-and-debugging-projects-for-realtime-rendering-in-unreal-engine).

| Path | Configured behavior | Intended use |
| --- | --- | --- |
| Windows quality | DX12/SM6, Lumen GI/reflections, TSR, Virtual Shadow Maps, hardware-ray-tracing support, and MegaLights at Epic shadow tier (`sg.ShadowQuality=3`) | Supported RTX 4070-class reference hardware at 1440p |
| Windows competitive | The same Windows cook at High scalability (`2`), with `r.MegaLights.Allow=0`, High shadow/GI/effects tiers, and no motion blur or gameplay depth of field | Lower-cost, readable combat presentation; requires profiling and tuning |
| macOS M1 Ultra | Metal SM6, software Lumen with mesh distance fields, TSR, conventional shadowing, Nanite fallback meshes/LODs, and no MegaLights or hardware ray tracing | 1080p M1 Ultra reference path |

The existing common renderer settings enable Lumen, mesh distance fields and
TSR. The Windows configuration targets DX12/SM6 only, with the DX11 fallback
shader format removed, and enables support for hardware ray tracing and
MegaLights. Epic describes MegaLights as production
ready in [UE 5.8's release notes](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-8-release-notes),
which also introduces `r.MegaLights.Supported` to control shader compilation,
and documents `r.MegaLights.Allow` as a [scalability switch](https://dev.epicgames.com/documentation/unreal-engine/megalights-in-unreal-engine).
The quality tier allows it; the competitive tier disables it. MegaLights is a
Windows quality option for hardware meeting Epic's [DX12/SM6/ray-tracing requirements](https://dev.epicgames.com/documentation/unreal-engine/hardware-and-software-specifications-for-unreal-engine),
not an assumption about every Windows GPU. The competitive tier still cooks
ray-tracing support, so its actual memory and frame-time benefit remains to be
measured.

Epic's [UE 5.8 Mac requirements](https://dev.epicgames.com/documentation/unreal-engine/macos-development-requirements-for-unreal-engine)
list software Lumen and TSR for M1+, while hardware Lumen/MegaLights require
M2+ experimentally and Nanite/Virtual Shadow Maps require M2+ in beta. The Mac
configuration therefore disables hardware ray tracing, MegaLights, Nanite, and
Virtual Shadow Maps. It keeps the common Lumen and distance-field settings;
[Lumen's software tracing path](https://dev.epicgames.com/documentation/unreal-engine/lumen-technical-details-in-unreal-engine)
uses mesh distance fields. `r.Nanite.ProxyRenderMode=0` selects the ordinary
fallback when Nanite is off, as described in Epic's [Nanite technical details](https://dev.epicgames.com/documentation/unreal-engine/nanite-technical-details).
Every production asset must still provide a usable conventional LOD or fallback
mesh and card-fur route. These files cannot create missing geometry or prove
that the current prototype assets are visually acceptable.

High (`2`) and Epic (`3`) are the source-controlled preset tiers. The Graphics
screen (**設定 → 画質**) applies them through Unreal's
[`UGameUserSettings`](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UGameUserSettings),
group by group, and Unreal saves them to `GameUserSettings.ini`
(`SoraGraphics` in `Public/SoraSettings.h`):

| Preset | Offered on | Scalability groups | TSR input | Frame cap | VSync |
|---|---|---|---|---|---|
| Mac | macOS | view distance, anti-aliasing, textures and landscape Epic; shadows, GI, reflections, post processing, effects, foliage and shading High (software Lumen, no MegaLights) | 75% | 60 | on |
| Windows Quality | Windows | all Epic, so shadows reach the MegaLights tier | 67% | 60 | on |
| Windows Competitive | Windows | view distance and textures Epic; anti-aliasing, shadows, GI, foliage, shading and landscape High; reflections, post processing and effects Medium | 75% | uncapped | off |

The first launch on a machine applies the platform's first preset once and
records that in the `SoraSettings` slot; after that the player's own values
stay. Resolution scale (50–100%), frame cap (30 to 240, or uncapped), vsync and
window mode (borderless or windowed on macOS, plus exclusive fullscreen on
Windows) are separate rows, and changing any of them makes the preset read as
Custom. The engine's settings are validated before the first change, because
applying them with no `GameUserSettings.ini` behind them would otherwise reset
the change. A `-game` run on this Mac confirmed the first launch wrote the Mac
preset's `[ScalabilityGroups]`, frame cap and vsync to
`Saved/Config/MacEditor/GameUserSettings.ini`. The
Mac build currently uses an M1-safe platform baseline across Macs, without a
separate M2+ experimental profile. Target-hardware validation must inspect the
effective renderer/scalability CVars, cooked shader formats, fallback meshes,
and visual output, then measure representative combat with `stat unit`,
`stat gpu` and GPU profiling. The acceptance targets are 60 fps at 1440p on the
RTX 4070-class Windows reference machine and 1080p on the available M1 Ultra.
No rendered session on the pinned UE 5.8.3 has measured these presets, and
neither frame rate nor photorealistic quality is verified.

## Implemented source

`ASoraGameMode` starts a procedural arena from the engine Entry map. `ASoraPlayerCharacter` and its equipment component provide first-person movement, sprint/jump, weapon selection, ammunition/reloading, line-of-sight gunfire, swept melee and explosive projectiles; `ASoraEnemy`, driven by `ASoraEnemyController`, provides simple enemy movement/attacks. [Source layout](#source-layout) lists the classes and files. Four arena layouts use generated architecture, cover, torii, lamps and production devices. The campaign has eight Japanese encounter outlines and 24 distinct production-site tasks with English subtitle text. The opening dojo encounter uses wooden-sword visuals and nonlethal sparring pupils; alien opponents appear only after the invasion. A site can require defeated opponents and an earlier site; the interface shows its name, and the world builder gives eight site types distinct prototype geometry and a visible activated state. Checkpoint loading rejects site progress inconsistent with those requirements. Ranged invaders miss on a fixed pattern rather than a random roll: every third shot, offset by spawn slot so a wave never misses in unison. The campaign still shares a restore/defeat/exit mission loop; these are not eight finished authored levels or a 6–8 hour experience.

### Source layout

The gameplay code is split by responsibility, so later feature work does not collide in one file. Public headers sit in `Source/SoraArena/Public`; implementations are grouped under `Source/SoraArena/Private`.

| Area | Files | Responsibility |
|---|---|---|
| Characters | `Private/Characters/`: `SoraCharacterBase`, `SoraPlayerCharacter`, `SoraEquipmentComponent`, `SoraViewmodelComponent`, `SoraEnemy`, `SoraEnemyController`, `SoraBoss`, `SoraPracticePawn` | Bodies, the hero, weapons, opponents and practice participants |
| Damage | `Private/Combat/SoraDamage.h`, `.cpp` | The one damage path for campaign and training attacks |
| Game flow | `Private/Game/`: `SoraGameMode`, `SoraCampaignDirector`, `SoraPracticeDirector`, `SoraGameEvents` | Session shell, offline rounds, kernel practice, event bus |
| HUD | `Private/HUD/`: `SoraHUD.cpp`, `SoraHUDStoryPanels.cpp`, `SoraHUDCombatPanels.cpp`, `SoraHUDCaptions.cpp`, `SoraHUDPanels.h` | Play panels on the canvas, shared drawing helpers and one function per panel |
| Front end | `Private/UI/`: `SoraFrontEnd.cpp`, `SoraFrontEndSettings.cpp`, `SSoraFrontEnd.cpp`, `SoraMenuInput.cpp`, `SoraCredits.cpp`, `SoraPracticeLobby.cpp`; `Public/SoraFrontEnd.h`, `Public/SoraPracticeLobby.h` | Every menu, built in C++ Slate: screen state, the settings screens and rebinding, the widget, key meanings, key names and prompts, credits, the practice lobby's choice |
| Settings | `Private/UI/SoraSettings.cpp`, `SoraCaptions.cpp`; `Public/SoraSettings.h`, `SoraSettingsSaveGame.h`, `SoraCaptions.h`, `SoraControlSaveGame.h` | Graphics presets, volumes, subtitles and accessibility, saved locally; sound captions |
| World | `Private/World/`: `SoraWorldBuilder.cpp`, `SoraMapNyaagyuEstate.cpp`, `SoraMapLanternWard.cpp`, `SoraMapSilkFoundry.cpp`, `SoraMapDebtCitadel.cpp`, `SoraWorldBuilderLighting.cpp`, `SoraWorldBuilderPractice.cpp` | Shared layout, one file of dressing per map, lighting, and the kernel-defined practice map |

- **Characters.** `ASoraCharacterBase` is the shared body: capsule and movement tuning, health, the cat model, the eye point where the weapon is held, the damage hooks and presentation of a kernel snapshot. `ASoraPlayerCharacter` is Nyaakoto: input gated by `SoraInputStates.h`, movement, dojo training, the campaign loadout and local control preferences. Its eye is the first-person camera. `USoraEquipmentComponent` owns ammunition per weapon, reloads, cooldowns, gunfire and shells, the yumi draw, swept and committed blade strikes, and the blade guard. `USoraViewmodelComponent` is the held weapon. For the hero it is the first-person viewmodel; for everyone else it is ordinary world geometry. `ASoraEnemy` is a ranged invader, a blade retainer or a dojo pupil, and owns its attacks. `ASoraEnemyController`, an `AAIController`, decides how the opponent moves and which attack runs. `ASoraBoss` is the final collector. `ASoraPracticePawn` presents one deterministic-practice participant other than the local player; the local player stays `ASoraPlayerCharacter`, driven by the kernel for the session.
- **Enemy scheduling.** Each opponent's tick calls its controller's `Think` at the point in the frame where the first prototype ran its bot logic. That is before the hero's tick, and the movement it requests is consumed on the next frame. Running the brain on the controller's own tick moved it after the hero's tick: a retainer killed by the katana then stopped turning one frame earlier, which changed the combat trace below. The pawn therefore keeps the slot until an AI change accepts that timing. Opponents do not use navigation-mesh pathing yet.
- **Damage.** Attackers call `SoraDamage::Deal`. Every character's `TakeDamage` calls `SoraDamage::Resolve`, which applies the shared rules: kernel-driven characters take no Unreal damage, and opponents never damage one another. It then asks the victim for its defenses (`AdmitDamage`: the pupil scoring gate, the dojo guard lessons, the retainer guard and parry) and for its defeat handling (`OnDefeated`).
- **Game flow.** `ASoraGameMode` is the session shell: menu and pause, mode selection, the title card, round results, notices and the input state. `USoraCampaignDirector` runs offline rounds, which are the eight chapters and the training arena. It owns the save and checkpoints, the opponents and the collector, the sites and the exit, the dojo forms, dialogue and objective text. `USoraPracticeDirector` runs the kernel session and presents it.
- **Front end.** `USoraFrontEnd` holds the menu screens (title, main, pause, chapter select, practice lobby, wallet, the settings hub and its five screens, credits, confirmations and the rebind dialog), the focused row and the last input device. `ASoraGameMode` owns it and keeps the world paused while a screen is open. `ASoraHUD` adds the C++ Slate widget `SSoraFrontEnd` to the viewport, gives it keyboard, pad and mouse focus while a screen is open, and returns input to play when it closes. No widget Blueprint assets are used.
- **Settings.** `USoraSettings`, which `ASoraGameMode` owns and loads at `BeginPlay`, keeps graphics in `UGameUserSettings` and everything else in `USoraSettingsSaveGame` (the `SoraSettings` slot): the six volume buses, English subtitles, subtitle size, speaker names, sound captions, the telegraph palette, hold or toggle for guard and sprint, campaign difficulty, auto-steer on horseback, reduced flashing and camera shake. Every change saves at once. `SaveSchema` defaults to 0 and new settings are stamped with the current schema, because Unreal writes only the properties that differ from the class default; a save without a schema or of another schema is discarded, and a value out of range falls back to its default. The settings own the English subtitle switch; the campaign save still carries an old copy, which `BeginPlay` overrides. Controls are the hero's `USoraControlSaveGame` (`docs/input.md`). What each setting reaches:
  - **Volumes.** Master sets the main audio device's volume. The other buses are stored and exposed as `BusGain` and `OnChanged` for the audio lane's sound classes (`docs/audio.md` §2); no sound class exists yet.
  - **Subtitle size and speaker names.** Dialogue and sound captions are drawn at 100%, 125% or 150%, and the dialogue panel grows upwards from the same bottom edge (`FSoraHUDFrame::DialogueLayout`). Speaker names can be hidden. Other HUD panels keep their sizes.
  - **Sound captions.** `USoraCaptions` captions other combatants' gunfire, shells, arrows, beams and swings, blocked and clashing blades, explosions and the collector's arrival, windups and defeat, each with its direction from the hero (ahead, left, right or behind). Repeats count up, at most four show, and each fades after two to four seconds of play. The HUD draws them at the top right while the setting is on. The audio lane can add its own with `Show`.
  - **Telegraph palette.** `SoraAccessibility::TelegraphColor` gives the story bible's two telegraph colours (§8) for Standard, red-green safe, blue-yellow safe and high contrast: `Cleave` for a cleave, a blow, a ring or any other area attack (amber in Standard) and `Lock` for a locked aim, a laser, a shot or a beam (cyan in Standard). The collector's cleave and beam warnings use it.
  - **Difficulty.** The bible's tiers 稽古 (Easy), 真剣 (Normal) and 免許皆伝 (Hard), in the order of `SoraBossRules` and `SoraStealthRules`. `SoraAccessibility::CampaignDifficulty(World)` gives the chosen tier to the systems that own its rules: windups +30% on Easy and −15% on Hard, per-difficulty boss health and timing tolerances, and a detected infiltration turning into a fight on Easy. It never scales the damage the hero takes. Practice and the kernel never read it.
  - **Auto-steer.** `AutoSteer()` is the accessibility setting that horseback beats marked `auto_steer: setting` read: the horse follows the route while the player keeps gait and aim.
  - **Reduced flashing.** The red edge when the hero is hit becomes a faint edge that fades out.
  - **Camera shake.** `SoraAccessibility::StartCameraShake` scales every shake by the setting. The game starts no camera shakes yet.
- **HUD and world.** `ASoraHUD::DrawHUD` draws play on the canvas and calls one panel function per panel, in the original draw order. `ASoraWorldBuilder::Build` creates the shared layout and calls each map's dressing at the point where it used to be inline, so every component keeps its name, transform and creation order.

`USoraGameEvents` is a world subsystem for game and PIE worlds. Audio, effects, telemetry and dialogue subscribe to it without editing gameplay files, for example `USoraGameEvents::Get(World)->OnDied.AddUObject(...)`. Each delegate carries a reflected `USTRUCT` payload. Listeners run synchronously inside the gameplay call and must not change combat state.

| Delegate | Raised when |
|---|---|
| `OnWeaponFired` | the hero fires a hitscan weapon, a shell or an arrow; an invader fires; the collector fires its debt beam |
| `OnMeleeCommitted` | the hero commits a katana, yari or naginata strike or swings another melee weapon; a retainer or pupil begins its windup |
| `OnStrikeResolved` | any of those strikes lands or misses, or the collector's cleave resolves |
| `OnGuarded`, `OnParried` | the hero guards or parries a retainer's blade; a dojo guard blocks a pupil's strike (`bDojo`) |
| `OnDamaged`, `OnDied` | `SoraDamage::Resolve` applies damage; health reaches zero (`bSparring` for a yielded pupil or a lost dojo bout) |
| `OnDetonated` | a shell explodes |
| `OnSiteRestored` | a production site is restored |
| `OnChapterStarted`, `OnChapterCompleted` | a campaign chapter round is built (`bResumed` from a checkpoint); the exit completes a chapter (`bLiberated` for the last) |
| `OnBossPhase` | the collector arrives, winds up, strikes, recovers or is defeated |
| `OnKernelEvent` | deterministic practice applies a kernel event; it passes the ABI event and its tick |

`SoraArena.Build.cs` also declares the modules that later work needs, so it does not have to be edited again: AIModule, GameplayTasks and NavigationSystem as public dependencies (`ASoraEnemyController` derives from `AAIController`), and Slate, SlateCore, UMG, Niagara, AudioMixer, MetasoundEngine, LevelSequence, MovieScene and CinematicCamera as private ones. Niagara and MetaSound are engine plugins enabled by default in UE 5.8.3, so `SoraArena.uproject` needs no plugin entries, and the build logs no plugin warning. The whole `Content/Data` directory is staged as NonUFS, so new data files ship without further edits; a probe file added under `Content/Data/campaign/` appeared in the target receipt's runtime dependencies. A Game target now fails to build when `Binaries/<platform>/libarena_ffi` or the Connect bridge is missing, or on a platform other than Mac and Win64. The Editor target builds and logs a warning instead. In a scratch copy of the project on 2026-09-25, a Game target without the kernel, or without the bridge, stopped with that message; the Editor target warned and built; and with both present the Game target compiled and linked. Its Xcode app finalization then hit the known generated-scheme pre-action failure that `build-mac.sh Development Game` retries, so no packaged app was produced there.

The version-four offline save records each chapter's defeated-opponent count, three restored production sites, and completed exit state after every objective event. Earlier prototype saves are not interpreted under these rules. Restarting the game, returning from practice, changing class in the menu, or retrying after defeat reconstructs that checkpoint. New campaign and chapter advance clear it; unfinished opponents respawn from the remaining count. Because New Campaign also resets the highest chapter reached, it opens a confirmation dialog whenever the save holds progress. The dialog starts on Cancel; only choosing the erase row erases the save, and Esc, Backspace or pad B withdraws it with the menu still open. Chapter select starts any chapter up to the highest reached: the saved chapter moves there and its checkpoint is cleared, while the chapter reach is kept. That also asks first. Round resets also destroy live campaign explosives before spawning the restored encounter, so a shell from a previous attempt cannot damage fresh opponents or advance their kill count. The save has no wallet, bond, or NFT state. The `SoraArena.Campaign.Playthrough` automation described below verifies save-slot serialization, world teardown, checkpoint restoration and retry after defeat in the editor; projectile cleanup and interactive play recovery still require a playtest.

Opening any front-end screen pauses the world through `AGameModeBase::SetPause`: actors, timers, the round timer and the practice clock stop, while the HUD and the Slate front end still draw. The front end holds input focus, so its keys work under the pause and none reach `UPlayerInput`; closing it clears the pause and flushes held keys. The first round is built by a next-tick timer before the title menu pauses anything.

The runtime catalog contains the six approved classes, eighteen approved weapon IDs, eight chapters and four maps. Its damage tuning applies **only to the campaign and ordinary training prototype**. The separately selectable deterministic practice mode reads combat tuning and all outcomes from the actual Rust kernel. Neither mode produces a qualified execution proof or settles money.

The camera enables UE 5.8 native first-person field of view and scale. The
owner's authored or fallback weapon mesh uses `FirstPersonPrimitiveType::FirstPerson`
with a 70-degree viewmodel FOV and 0.6 scale; this keeps the weapon readable while
reducing clipping into nearby architecture. It changes presentation only. The
current source does not yet include a finished first-person feline paw rig or
the separate world-space representation needed to validate self-shadowing and
reflections. The implementation follows Epic's [first-person rendering guide](https://dev.epicgames.com/documentation/unreal-engine/first-person-rendering)
and [UE 5.8 component API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UPrimitiveComponent);
actual rendering still needs the pinned editor and target hardware.

Japanese is the primary UI/story language. Catalog schema 2 includes six speaker identities and three timed, original Japanese dialogue cues per chapter, each with an English subtitle. A chapter started fresh opens on a title card before its dialogue and round timer begin. The card shows the SORA insignia, the chapter number, the Japanese title, narrative and objective, and, with subtitles on, the English title, narrative and objective from `title_en`, `narrative_en` and `objective_en`. Enter skips it; otherwise it closes after nine seconds. Combat is held while it shows. A resumed checkpoint goes straight back to play. The narrative used to be a lower-third notice that was hidden whenever a dialogue cue was showing; it now appears in full on the card. A notice raised during dialogue is drawn in a one-line strip above the cue instead of waiting for a gap between lines. The HUD displays a cue while combat and objectives continue; opening dialogue pauses with the campaign menu and does not replay when an objective checkpoint is resumed. The catalog loader requires, and the HUD shows with subtitles on, the English names of maps, classes and chapters. English subtitles are on by default and persist through the save setting. No dialogue cursor is saved. `scripts/unreal/validate_content.py` checks speaker references, bounded nonoverlapping timing, text lengths, and every catalog glyph against the shipped Noto Sans CJK JP font. The font includes its SIL OFL license and copyright notice. Voice acting is not recorded; timing and readability still need an Unreal playtest.

`DefaultGame.ini` sets the game culture to `ja`, replaces inherited packaging cultures with `ja` and `en`, and selects the `EFIGSCJK` ICU data preset, which contains both Japanese and English. Without a compiled game resource, Unreal's game startup could select English despite the culture setting.

The interface's strings are Unreal localization. They cover the front end, the settings screens, key and control names, the wallet screen's labels and states, the credits' own lines, sound captions, the HUD top bar and the game mode's menu notices, 339 keys in all. Each is an `NSLOCTEXT` whose native text is Japanese. Its English subtitle is the same namespace and key's translation in `Content/Localization/Game/en/Game.po`, the gettext file Unreal's localization dashboard imports and exports. `scripts/unreal/native_japanese_localization.py` does the following:

- gathers every `NSLOCTEXT` in `Source/SoraArena` and refuses one key with two native texts;
- merges the keys into `Game.po`: a new key gets an empty English entry, a key whose Japanese changed is marked fuzzy with the old Japanese, and a key gone from the source is dropped;
- stops until every entry has English that uses the same `{Name}` arguments as its Japanese and contains no Japanese;
- compiles `Game.locmeta` (native `ja`, compiled `ja` and `en`), `ja/Game.locres` and `en/Game.locres`, in the compact version-1 format. Each English entry carries the CRC of the Japanese it translates.

It also fails if any Japanese string literal in the interface sources (`Private/UI`, the HUD frame and captions, the game mode and the public UI headers) sits outside `NSLOCTEXT`. It lists the files that still hold Japanese literals and belong to other lanes: the story and combat HUD panels, the campaign and practice directors, the wallet and kernel subsystems and the quote preflight. `--check` verifies the PO file and all three resources without writing, and `validate_content.py` checks the same resources.

At run time the Japanese line is the `FText` in the game culture. `SoraText::English` reads the English resource with Unreal's own loader and looks up the same key, so both lines show at once. Like Unreal's own lookup, it refuses a translation whose source CRC does not match the Japanese. A key with no current English logs an error once and shows no English line rather than the wrong words. `SoraText::Format` fills a pattern and its English with each argument in its own language. Staging copies only `*.locres` and `*.locmeta`, not the PO file. With game localization loaded, a `-culture=en` launch would show English on the primary line as well. Authored story dialogue stays bilingual in the campaign data.

`SoraArena.Localization.NativeJapanese` uses Unreal's resource loader to check the metadata, title key and source hash, runtime culture when run with `-game`, and the separately authored English subtitle. It passed in an interim UE 5.8.3 `-game` run with `native=ja active=ja title=猫柳生 english_subtitle=present` and no Japanese-to-English fallback warning. `SoraArena.Localization.EnglishSubtitles` loads both resources with Unreal's loader and checks four things. The English must cover exactly the Japanese keys, and every entry must be native, translated from the current Japanese, free of Japanese and found by the runtime lookup. Patterns must fill each language with its own arguments. A translation of older Japanese, and a key without one, must give no English, and the missing key must log exactly once. A package built from the main checkout on the pinned 5.8.3 engine remains to be verified. This game setting does not change the Unreal Editor's preferred language.

The front end's IrohaConnect wallet screen calls the real `UArenaWalletSubsystem`: pair, open an available wallet deep link, and disconnect, with the status, signing state, unverified Join preview and pairing QR code beside them. It never marks a bond funded merely because a wallet connects. Details are in `connect.md`.

`UArenaKernelSubsystem` dynamically loads the actual staged Rust library, requires its current presentation exports, requires exactly ABI 3, executes a sixty-tick zero-deposit diagnostic, and reads its actual qualification flag. Missing exports or any other ABI version reject the library before layout-sensitive calls; no fallback or alias is provided.

### Deterministic practice source

The front end's practice lobby (**武芸稽古**) chooses mode, arena, class, special weapon, difficulty and player count as an `FSoraPracticeLobbySelection` and calls `ASoraGameMode::StartPracticeFromLobby`. Until `USoraPracticeDirector::StartPractice(FSoraPracticeConfig)` lands, the class, arena and special weapon reach the kernel, which creates a ten-minute, six-participant free-for-all practice session with zero base bond and zero deposits. Five local bots generate ordinary canonical inputs; they have no privileged damage or movement path. A visibility graph around the reference obstacles supplies simple bot navigation. This is offline practice, not networked P2P play.

The shared `FSoraPracticeClock` advances at 60 Hz with at most eight steps per rendered frame. Menu time is discarded; a long rendering hitch slows simulation time instead of skipping input ticks. Each step reads player health, positions, cooldowns and respawns, consumes that tick's events before advancing, and updates stable-ID projectile visuals. Millimeters convert to Unreal centimeters and feet positions gain the queried capsule half-height. Map obstacles and capsule/eye dimensions come from native queries. Perimeter lines mark movement limits without inventing bullet-blocking boundary walls.

In this mode, Unreal CharacterMovement is disabled, transforms come from snapshots, and Unreal damage/healing callbacks cannot change health. Tracers clip cosmetically against displayed geometry; hit markers come only from kernel damage events. The HUD displays actual kernel ammunition, magazine capacity, reload ticks, stamina/cooldown, and weapon-bound charge progress. Every practice pawn's weapon pose follows that same charge snapshot, providing a provisional visible windup cue. The combat HUD shows remaining match time; raw state hashes remain available through diagnostics and replay reports. R queues the canonical reload input (bit 32); bots request the same input when empty. Magazine-zero melee weapons display their melee label. No Unreal timer can refill kernel ammunition or complete a charge. Campaign ammo/reload data is not used for practice counters. The lobby's special weapon decides the loadout the player enters with; loadouts remain fixed during the session. Right click still invokes the class melee attack. Death triggers the kernel's automatic respawn with no financial movement. Windup visibility and readability still require an Unreal playtest.

`scripts/unreal/verify_practice.py` runs the real staged library through 72 map/class/loadout scenarios and repeats 86,400 ticks across independent handles. It checks matching transcript hashes, zero deposits, invalid-input atomicity and terminal immutability. A targeted clear-sightline scenario verifies death and respawn events. It also compiles and executes the exact shared clock header at multiple frame rates and under long hitches, pauses and invalid deltas. The report is written to `Saved/Diagnostics/practice_replay_report.json`. These native checks do not replace the still-pending Unreal compilation, input, visual and play tests.

`scripts/unreal/verify_parity.py` supplies the stronger cross-platform regression gate: repository-pinned binary canonical controls, explicit source/runner and ABI-layout identities, and expected state/event/presentation digests generated from the actual macOS kernel. It executes 73 scenarios and 44,100 ticks against immutable expectations, including all map/class/loadout combinations and a death/respawn case. ## Controls

Every menu is the Slate front end. It shows its own device-aware prompts, which switch between keyboard and pad labels with the last key, stick, click or mouse move.

| Key | Pad | In menus |
| --- | --- | --- |
| Arrows / WASD | D-pad / left stick | Move between rows; left and right change an option |
| — | LB / RB | Change an option |
| Enter / Space | A | Choose; on the title screen any key begins |
| Esc / Backspace | B | Back; closes a dialog without acting; resumes from the pause menu |
| — | Start | Resumes from the pause menu |
| F10 | — | Toggle English subtitles |
| Mouse | — | Moving over a row focuses it; click chooses, the arrows change an option, the wheel scrolls, right click goes back, prompts are clickable |
| On a Controls binding row: Enter, a click | A | Rebind with that device: the next key, mouse button or pad button binds; Esc or Start cancels |

| Key | Pad | In play |
| --- | --- | --- |
| Enter | A | On a chapter title card, skip it; on a result screen, continue |
| Esc | Start | Open the pause menu, which pauses the world |
| WASD / mouse | Sticks | Move / aim |
| Left click / right click | RT / B | Fire / melee |
| 1 / 2 / 3 | D-pad left / down / right | Primary / melee / special weapon |
| 4 / 5 / 6 | RB | Yumi / yari / naginata in the campaign (RB steps through them) |
| R / E | X / Y | Reload / activate nearby workshop or exit gate |
| Shift / Space | L3 / A | Sprint / jump |
| F10 | — | Toggle English story subtitles |
| Ctrl / Q | LT / LB | Block / class ability, in deterministic practice |

These are the defaults. Every play-only action and the four movement keys can be rebound on the Controls screen, and guard and sprint can be set to toggle; `docs/input.md` has the rules.

Pad A is Enter on the title card and result screens and Jump in play. `Source/SoraArena/Public/SoraInputStates.h` lists the game states in which each action may act: the chapter title card, play, and result screens. No action acts in a menu, where the front end holds input. `ASoraPlayerCharacter` binds every press through that table and ignores it outside those states. Every press in one input frame is judged by the state that frame began in, so the A press that skips the title card does not also jump. Thumbstick clicks carry nothing that acts outside play, because players press them by accident while moving or aiming.

All special weapons are available for offline practice. No bonds or NFT ownership are required for this development preview. Campaign weapon selection preserves that weapon's ammunition, and campaign death retries from the latest saved objective checkpoint. Deterministic practice locks the selected weapon for each session and automatically respawns defeated players. Neither route risks assets.

## Verification and remaining gates

`python3 scripts/unreal/validate_content.py` checks the catalog IDs/assignments, Japanese default, English narrative, title, objective, map, class and weapon-name coverage, the input layout (below), source FBX headers, pinned font hash and—when fontTools is available—actual glyph coverage of all Japanese catalog/source text. It runs `scripts/unreal/check_input_conflicts.py`, which can also be run on its own. That script reads `Config/DefaultInput.ini`, the state table in `SoraInputStates.h` and every source in `Source/SoraArena` except the automation tests. Unreal matches key names without regard to case, and so does the script: `spacebar` and `SpaceBar` are one key. It fails in these cases:

- two actions that share a key can act in the same state;
- an action acts in the Menu state, where the front end holds input;
- an action that acts outside play sits on a thumbstick click;
- a mapped action has no state row, or a row names an unmapped action;
- a source binds input other than through the state gate. Outside the `BindPress` and `BindRelease` helpers in `SoraPlayerCharacter.cpp`, any `BindAction`, `BindKey`, `BindTouch`, `BindGesture`, `BindAxisKey`, `BindVectorAxis` or `AddActionBinding` call fails, whatever form its name takes, as does any use of the input component's binding arrays. `BindAxis` is allowed only in `ASoraPlayerCharacter::SetupPlayerInputComponent`, with a `TEXT` name. Comments and strings are ignored;
- `BindPress` no longer asks `AcceptsInput`, or `SoraPlayerCharacter.cpp` no longer defines `SetupPlayerInputComponent`, `BindPress` or `BindRelease`;
- the Controls screen's table, `SoraInput::Remappable`, lists a control that acts outside play, an unmapped action, the same control twice, or a movement half no keyboard key drives, or misses an action that acts only in play;
- Menu loses Escape or Start, which cancel a rebind, or `SoraPlayerCharacter.cpp` no longer checks remaps against the table.

Its built-in self-test must reject known-bad layouts before it checks the project, including a menu command on the sprint stick click, an action live in menus, and each bad rebind table above. `stage_kernel.py` validates the loaded binary independently of the Unreal wrapper, including map/weapon queries, presentation snapshots, per-tick events and stable projectile IDs. Blender generation and rig export ran successfully.

### Asset import

`scripts/toolchain/import-mac.sh [log-directory]` runs the three editor scripts of step 4 in order, each in its own `UnrealEditor-Cmd -ExecutePythonScript=<script> -unattended -nopause -nullrhi` process. The default log directory is `Saved/Import/<UTC time>/`, with one log per step. The script selects the engine and Xcode through `doctor.py`, as `build-mac.sh` does. It refuses to run in these cases:

- less than 30 GiB of free disk before any step (override with `SORA_MIN_FREE_GIB`);
- `build-mac.sh Development` fails. The script runs it first, because the importers load the project module and Unreal does not rebuild it with `-unattended`. UBT rebuilds only what a source, header or build rule change requires; its log is `build.log` in the log directory;
- the host check `validate_imported_assets.py --source-only` fails a source hash or manifest identity.

`UnrealEditor-Cmd` can exit 0 after a Python exception, so the exit code alone proves nothing. Each step must exit 0, log no `LogPython: Error` or Python traceback, and log its completion marker: `SORA_ASSET_IMPORT_COMPLETE`, then `NYAAGYU_PBR_READY`, then `SORA_ASSET_VALIDATION_COMPLETE` with exactly the package count that the host check reported. It guards `Config/` as the automation runner below does. The importers replace existing packages, so the script can be run again after the source art changes.

The output, about 815 MB under `Content/Generated` and 11 MB under `Content/ArtReview`, is not tracked in Git, although `.gitignore` does not exclude it yet; every checkout regenerates it from the hash-pinned sources. ### Headless automation

`scripts/toolchain/run-automation-mac.sh [Filter[+Filter...]] [output-directory]` runs Unreal automation in the Mac editor with `UnrealEditor-Cmd -ExecCmds="Automation RunTests <Filter>;Quit" -unattended -nopause -nullrhi`. The default filter is `SoraArena`, and the default output is `Saved/Automation/<UTC time>/`, which holds `editor.log` and Unreal's `report/index.json`. The script selects the engine and Xcode through `doctor.py`, as `build-mac.sh` does; `UE_ROOT` overrides the default engine location. It refuses to run in these cases:

- less than 30 GiB of free disk (override with `SORA_MIN_FREE_GIB`);
- `build-mac.sh Development` fails. The script runs it first, because Unreal does not rebuild the project module with `-unattended` and a stale module would test old code. UBT decides what is stale from every source, header (including the kernel's `arena.h`) and build rule, and does nothing when the module is current. Its log is `build.log` in the output directory.

The script prints each test's result, error count and warning count. It exits nonzero if any of these happen:

- a test reports a state other than `Success`;
- the number of tests reported differs from the number Unreal found;
- no test matches the filter;
- the editor exits with an error even though every test passed;
- a file under `Config/` changed, appeared or disappeared during the run.

Two engine features rewrite project config at every editor start: the Enhanced Input editor module upgrades the default input classes in `Config/DefaultInput.ini`, and AndroidFileServer writes a new security token to `Config/DefaultEngine.ini`. `scripts/toolchain/editor-config-guard.sh`, which both runners source, turns both off for the editor process with command-line ini overrides (`EnhancedInput.bEnableAutoUpgrade=0` and a fixed AndroidFileServer token), which the editor never saves. The editor then leaves `Config/` alone, and the tests run with the legacy `UPlayerInput` and `UInputComponent` that a packaged game uses. The guard hashes every file under `Config/` before the editor starts and again when the script exits. It never copies files back or deletes them, because the working tree is shared and a change may be someone else's edit. It names each changed file, leaves it as it is and fails the run.

The tests below start real standalone game worlds. `ASoraGameMode` comes from the world settings, and a player controller possesses `ASoraPlayerCharacter`. Each test uses a unique save slot with its control slot, `<slot>_Controls`, and settings slot, `<slot>_Settings`, and deletes all three at the end. None reads or writes the player's `SoraSoloCampaign` save, `SoraControlsV1` control preferences or `SoraSettings` settings. Their settings are detached from the engine: graphics go to a transient `UGameUserSettings` that is never applied, and no volume reaches the audio device, so no test changes the editor's graphics or writes `GameUserSettings.ini`.

The card waits behind the title screen and the main menu, and appears on Continue with no competing notice. `SoraArena.Input.IsolatedControlProfile` checks that the key tests cannot pick up this machine's control profile. Two more world tests replay scripted fights through the same simulated keys:

- `SoraArena.Campaign.CombatTrace` plays four fights: the first invasion chapter against a blade retainer (guard, parry, katana cuts, carbine, reload, yumi, yari, sprint and jump), the dojo lessons and scored bouts, the final chapter restored at seventeen defeats (the collector's beam and cleave, carbine fire, its defeat, the last site and the liberating exit), and the training arena with the Hanabi class (grenade and mortar shells and the kanabō). Every frame it records the hero, each opponent and each live projectile, then logs the SHA-1 of that trace as `SORA_COMBAT_TRACE` and writes the trace to `Saved/Diagnostics/combat_trace_<fight>.txt`. It checks each fight's outcome. The hashes are a behaviour fingerprint: a change that claims to keep behaviour must reproduce them, and the trace files show the first differing frame when it does not. They are not pinned in the test, because an intended combat change, or another compiler or platform, may legitimately change them.
- `SoraArena.Events.ScriptedFight` plays each of those fights again with a listener on every `USoraGameEvents` delegate. Each fight must trace identically with and without listeners. The test then checks the announced events: for example, the retainer's guarded and parried cuts, the hero's committed katana and yari strikes, each defeat with its killer, carbine, arrow and invader fire, the restored site, the dojo's guarded pupil strikes and yielded bout, the collector's arrival, windups, strikes, recoveries and defeat, the liberating chapter completion, shells and their detonations in the arena, and a chapter start only for campaign rounds. Finally it runs 300 frames of deterministic practice: each frame must announce exactly the kernel events of its step, with that step's tick.

`SoraArena.UIRendered.FrontEndScreens` is a client-only test, so the NullRHI editor suite never lists it. It runs in a rendering game: `scripts/toolchain/run-editor.sh -game -windowed -ResX=1280 -ResY=720 "-ExecCmds=Automation RunTests SoraArena.UIRendered;Quit"` (with the two `-ini` overrides of `editor-config-guard.sh`). It sends keys through `FSlateApplication` to the focused widget, as a player's are, and moves and clicks the mouse on a drawn row (hover focuses it, a left click opens it, a right click goes back). It visits every title-context screen, the five settings screens, the Controls bindings and the rebind dialog, and saves each with its UI to `Saved/Screenshots/SoraFrontEnd/<width>x<height>/` (nineteen shots). It then enters the round and checks where keys go as the HUD hands focus between the game viewport and the front end: in play a held X reaches play input; Esc opens the pause menu, which takes keyboard focus, and X held under it never reaches play input; Esc resumes and focus returns to the game; a menu a director opens (`SetMenuOpen(true)`) lands on the main menu with focus, and E held under it never reaches play input. The round runs on a throwaway save slot, so the player's campaign is never written, and no setting changes. Like any launch, the first run on a machine applies the platform's graphics preset and writes the `SoraSettings` slot.

`SoraArena.Connect.CancelledSignatureLatch` needs no world. Cancelling a request that is awaiting a signature latches the cancelled request's late reply; the latch used to be cleared only by a late reply or a disconnect. The test checks that the latch keeps the cancelled request's own signing deadline and absorbs replies until then. After the deadline `TickSession` clears it without ending the approved session or reporting a failure, so new requests can be signed again. A reply that arrives later still fails closed: with no request pending it is unsolicited, and during a new request its signature cannot finalize the different payload.

The campaign test calls the GameMode entry points directly, and the practice test runs the handlers that `SetupPlayerInputComponent` binds. The combat-trace fights put a retainer, a pupil, the collector and several invaders in range of the hero, but they cover only those scripted situations, not enemy AI in general, combat feel or pacing. The canvas HUD's rendered layout, including the chapter title card, the enlarged dialogue panel and the sound captions, cannot be drawn in a NullRHI world and remains unverified; only the dialogue panel's geometry is checked. The front end's is checked by the rendered client test above. Practice determinism is checked on one host and one binary; cross-platform parity remains `verify_parity.py`'s job. The tests ignore only the world builder's documented missing-`/Game/Generated` fallback errors, which the asset tests below check separately.
